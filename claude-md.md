## Project Overview
Automated weekly leads forecasting pipeline replacing a manual Google Sheets model. The system pulls lead data from Looker, stores it in Supabase, computes a baseline forecast, and pushes results to Google Sheets.

## Architecture

```
Looker (scheduled daily 9AM) 
  → Webhook (JSON — Simple format) 
  → Supabase Edge Function (looker-leads-ingest, slug: bright-worker)
  → Supabase PostgreSQL table (leads_weekly_actuals)
  → SQL view (weekly_leads_by_bu) computes WoW, YoY, avg_wow_3yr
  → SQL function (generate_forecast) produces baseline forecast
  → Python script (push_to_sheets.py) pushes to Google Sheets
  → Google Sheets remains the interactive control panel for manual adjustments
```

### Tables

#### leads_weekly_actuals
Raw Looker data. ~185,748 rows covering 2022-01-01 through current. Wipe-and-reload daily.
```sql
- id BIGINT (auto-generated)
- "Reporting Date" DATE
- "Reporting Week" DATE
- "Business" TEXT
- "Audience (Sales)" TEXT
- "Lead Source Group" TEXT
- "Ad Spend  (Total, incl VSX)" TEXT  -- note: two spaces before parenthesis
- "Leads (Valid)" NUMERIC
```

**IMPORTANT:** Looker sends column names with leading spaces on "Reporting Date" and "Reporting Week". The Edge Function trims all keys before processing.

**IMPORTANT:** Ad Spend column has ONE space before parenthesis in Looker's JSON output but TWO spaces in the Supabase table. The Edge Function handles both.

#### lead_source_mapping
Reference table for lead source name mapping.
```sql
- id BIGINT
- "Looker Lead Source" TEXT
- "Model Lead Source" TEXT
```

#### week_calendar
Custom Sunday-start week numbering. Week 1 = the Sunday-start week that contains January 1st.
```sql
- week_start DATE (always a Sunday)
- week_year INTEGER
- week_number INTEGER (1-52)
```
Examples:
- Week 1 of 2024 = 2023-12-31
- Week 1 of 2025 = 2024-12-29
- Week 1 of 2026 = 2025-12-28

Covers 2022 through 2028.

#### leads_forecast
Forecast output table. Generated by `generate_forecast()` function.
```sql
- id BIGINT
- "Business" TEXT
- week_number INTEGER
- week_year INTEGER
- week_start DATE
- py_leads NUMERIC

- avg_wow_3yr NUMERIC

```

### Views

#### weekly_leads_by_bu
Aggregates daily data to weekly by business unit. Computes:
- total_leads per week per BU
- wow_pct (this week / prior week × 100, full precision, crosses year boundaries)
- py1_leads (prior year leads, matched by week_number)
- yoy_pct (total_leads / py1_leads × 100, full precision)
- wow_py1, wow_py2, wow_py3 (WoW for 2025, 2024, 2023 respectively)
- avg_wow_3yr (average of wow_py1, wow_py2, wow_py3 — excludes NULLs, full decimal precision)

**CRITICAL:** All calculations use FULL DECIMAL PRECISION. No rounding anywhere in the view or forecast function. This was validated to match the Google Sheet exactly.

### Functions

#### generate_forecast()
PL/pgSQL function that:
1. Deletes all existing forecast rows
2. Creates a temp table (forecast_input) that pre-joins week_calendar, actuals, prior year leads, and avg_wow (from 2023-2025 only, NOT all years)
3. Loops through every week for every BU from 2022-2028
4. For actual weeks: stores the actual leads
5. For forecast weeks: computes baseline using the blended formula
6. The current incomplete week (week_start >= current Sunday) is treated as FORECAST, not actual
7. Drops the temp table

## Forecast Methodology

### Top-Line Forecast Formula (per BU, per week)
```
baseline = average(yoy_signal, wow_signal)

where:
  yoy_signal = trailing_4wk_avg_yoy × prior_year_leads_this_week
  wow_signal = avg_wow_3yr × prior_week_forecast

  trailing_4wk_avg_yoy = average of the last 4 weeks' (forecast_or_actual / prior_year_leads × 100)
  avg_wow_3yr = average of WoW ratios for this week_number across 2025, 2024, 2023
```

### Key Details
- WoW is a RATIO not a growth rate: 110% means this week = 110% of prior week
- YoY is a RATIO: 95% means this year = 95% of prior year
- avg_wow_3yr uses ONLY 2023, 2024, 2025 (not all historical years)
- The trailing 4-week YoY uses implied YoY from forecasted weeks (forecast / PY leads), not just actuals
- Each week's forecast feeds the next week's calculation (rolling chain)
- The current partial week is excluded from actuals and forecasted instead
- All calculations maintain full decimal precision (no rounding)

### Forecast Cascade (not yet built in Supabase)
1. **Top-line forecast** per BU (DONE — matches Sheet exactly)
2. **Lead channel/source allocation** — weighted blend of CY mix (e.g. 60%) and PY mix (40%), weights adjustable per week
3. **Audience allocation** — same weighted blend methodology applied within each channel
4. Manual nominal lead adjustments at both levels, with automatic redistribution to maintain totals

### Manual Adjustments (handled in Google Sheets)
- Per-week forecast adjustment percentage (e.g., +5% for Easter, -33% for holidays)
- CY/PY weight overrides per week (can vary week to week)
- Nominal lead adds/subtracts per audience with automatic rebalancing
- Holiday flags, spring break periods, tROAS change events

## Known Issues / Gotchas
- Looker adds leading spaces to some JSON field names (" Reporting Date" instead of "Reporting Date")
- Looker's Ad Spend column has inconsistent spacing (1 vs 2 spaces before parenthesis)
- Supabase Edge Functions require JWT verification to be OFF for Looker webhooks
- The Edge Function slug is "bright-worker" (default name that stuck) even though it's named "looker-leads-ingest" in the dashboard
- Windows PowerShell requires `Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser` before activating venv
- The Supabase free tier SQL editor has a default statement timeout; generate_forecast() runs fine within it now using the temp table approach
- Week 1 WoW is NULL because there's no data before Week 1 of 2022 (the earliest year)
- ISO week numbers do NOT match the custom week calendar — always use the week_calendar table
